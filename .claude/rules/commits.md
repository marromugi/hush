# コミットのルール

コミットメッセージの書き方を決めます。文の書き方は `.claude/rules/writing.md` に従います。

git log は、あとで経緯を調べるために読みます。diff を見なくても、なぜ変えたのかが分かるように書きます。

## 形式

Conventional Commits の形式で書きます。件名と本文の間には空行を入れます。

```
<type>(<scope>): <要約>

背景:
- なぜこの変更が必要になったかを書きます。

変更:
- 何を変えたかを書きます。

判断:
- 選ばなかった案と、その理由を書きます。

確認:
- 何を実行して、どうなったかを書きます。

Co-Authored-By: ...
```

本文の見出しに `#` は使いません。エディタでコミットすると、`#` で始まる行は消えるからです。

## 件名

type は次の表から選びます。

| type | 使う場面 |
|---|---|
| feat | 機能の追加 |
| fix | 不具合の修正 |
| refactor | 動きを変えない整理 |
| perf | 速さや容量の改善 |
| test | テストの追加や修正 |
| docs | 文書の変更 |
| build | ビルドや依存の変更 |
| ci | CI の変更 |
| chore | 上のどれにも当たらない作業 |

- scope には、変えた範囲のモジュール名かディレクトリ名を書きます。
- 範囲が広くて一つに決まらないときは、scope を省きます。
- 要約は日本語で書きます。「〜を追加」のように名詞で終えて構いません。
- 要約は 40 文字以内にします。

互換性がなくなる変更では、type の後ろに `!` を付けます。

- 例えば、vault.json や日記ファイルの形式を変えるときです。
- 本文の「変更」に、古いデータがどうなるかを書きます。

## 本文

本文は必ず書きます。件名だけのコミットは作りません。

書くのは、diff から読み取れないことです。

- 変更のきっかけです。不具合の症状や、仕様のどこに当たるかを書きます。
- 検討して選ばなかった案です。理由も一緒に書きます。
- 後で困りそうな前提や、わざと残した制限です。

書かないのは、diff を読めば分かることです。

- 変数名やファイル名の一覧は書きません。
- 「〜を修正しました」だけの項目は書きません。何がどう変わるかを書きます。

「判断」は、他の案を検討しなかったときだけ省きます。他の項目は省きません。

## コミットの分け方

一つのコミットには、一つの目的だけを入れます。

- 整形だけの変更は、中身の変更と分けます。
- 依存の追加は、それを使う変更と同じコミットに入れます。
