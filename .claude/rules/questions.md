# 質問の書き方

AskUserQuestion で開発者に聞くときのルールです。スキルの中でも外でも適用します。

文の書き方は `.claude/rules/writing.md` に従います。ここでは、質問に何をどの順で書くかだけを決めます。

開発者は、質問のダイアログだけを見て答えます。直前のメッセージは見えていないものとして書きます。issue や PR も開いていないものとします。

## 仕様で説明する

質問は仕様の話として書きます。実装や作業の手順の話にしません。質問文は次の順に組み立てます。

1. 背景です。どの機能の、どんな場面の話かを書きます。
2. 何がどうなるかです。使う人から見た、いまの動きと困ることを書きます。
3. 何ができるようになるかです。決めた後に、使う人ができることを書きます。
4. 最後に、何を決めるのかを一文で聞きます。

レビュー、CI、自動チェックのような作業の手順は、答えに関わるときだけ書きます。マージや有料の実行の可否を聞くときも同じです。その変更で何ができるようになるかを先に書きます。

## 言葉

- issue や PR の番号は、括弧で添えるだけにします。番号を主語にしません。
- よそで付けた呼び名は使いません。「案 A」「V1」「ガード」のような名前です。前のメッセージや issue の中でしか通じないからです。中身を普通の言葉で書きます。
- 型やファイルの名前も、質問文には出しません。
- 実装の中の考え方で説明しません。番号、キュー、状態のような言葉です。使う人に何が見えて、何が聞こえるかで書きます。

## 選択肢

- description には、選ぶと何ができるようになるかを書きます。何ができないままかも書きます。
- preview にはコードをそのまま書きます。文章で説明しません。
- 実装の話は preview にだけ書きます。
- 推奨を付けるときは、その理由を description に書きます。

## preview のコード

preview は等幅の枠で表示されます。そこに、選んだ後のコードを具体的に書きます。

- 先頭の行に、ファイルのパスをコメントで書きます。
- 呼ぶ側のコードが変わるなら、呼ぶ側を書きます。
- 中身の書き換えなら、変更前と変更後を並べます。
- 必要な行だけに絞ります。

## 使う人から説明できない話

リファクタリングやコードベースの整理は、使う人から見た動きが変わりません。この場合は、仕様の順に当てはめません。

- 質問文には、何を整理したいのかと、困っていることを普通の言葉で書きます。
- 各選択肢の preview に、変更前と変更後のコードを書きます。
- 何をどうしたいのかは、コードで見せます。文章だけで説明しません。

## 前置きのメッセージ

前置きのメッセージは補足だけにします。答えるのに要ることは、質問文か preview に入れます。

## 例

悪い例です。作業の経緯と、よそで付けた呼び名に頼っています。

```
#580 と #583 に共通する、Player の番号の設計をどう進めますか。
読み上げは返答ごとに番号 0 から数えますが、
インターフェース（packages/voice/src/player.ts）は
返答をまたいだ番号の扱いを決めていません。
```

良い例です。質問文は、使う人から見た動きだけで書いています。

```
音声対話で、エージェントが声で返答する場面の話です。
いまは、前の返答を話し終える前に次の返答が来ると、次の返答が声になりません。
エラーで止まり、そこで会話が途切れます。
どちらかに決めると、返答が重なっても会話が続きます。
重なったとき、どちらの声を優先しますか。
```

選択肢と preview です。preview には、呼ぶ側のコードを書いています。

```
選択肢: 前の返答を最後まで話す
説明:   前の返答を話し終えてから、次の返答を話します。
        待つ間、次の返答は遅れて聞こえます。
preview:
  // packages/voice/src/player.ts を使う側
  // 呼び方は今のままです。前の返答が終わるまで待ちます。
  await player.play(0, nextReply);
```

```
選択肢: 次の返答に切り替える
説明:   次の返答が来たら、前の返答をその場で止めます。
        前の返答の残りは聞こえません。
preview:
  // packages/voice/src/player.ts を使う側
  player.stop();
  await player.play(0, nextReply);
```
